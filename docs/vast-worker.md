# Vast.ai GPU worker image

Docker image for the Vast.ai fallback of the vocal-separation backend
(`odd/tasks/vast-gpu-fallback.md`). A Vast instance started from it separates
immediately: no `apt-get`, no `pip install`, no model download at run time.

Image: `ghcr.io/loonbac/shirley-vast-worker` (tags `:<git-sha>` and `:latest`).

## What is inside

| Piece | Why |
| :--- | :--- |
| Writable CUDA PyTorch build (`torch` 2.5.1, cu124 wheels) | The separation models are PyTorch RoFormers; the cu124 wheels carry the whole CUDA runtime, so the host only has to provide a driver supporting CUDA **>= 12.4** — nothing CUDA is baked into the image and no `nvidia/cuda` base is needed. |
| `audio-separator[gpu]==0.48.0` in `/opt/venv` | Pinned, exactly the package the generated script imports. `[gpu]` brings `onnxruntime-gpu`; `audio_separator` imports `onnxruntime` unconditionally, and the CPU build would make its ONNX paths unusably slow on a GPU worker. |
| `diffq` compiled from source, in the builder stage | `diffq` is a **mandatory** dependency of `audio-separator` (`Requires-Dist: diffq`) and has no linux wheel, so `pip install` compiles `bitpack.c`. That is the failure the live probe saw; see "Why the probe failed" below. |
| ffmpeg + ffprobe | The script encodes the averaged stem to MP3 320k and probes its duration. On a fresh Vast instance `apt-get install ffmpeg` costs 220-480s — the largest single saving of this image. |
| `libsndfile1`, `libsamplerate0` | Native libraries behind the `soundfile` and `samplerate` Python packages the separator imports. |
| Both separation models in `/opt/models` | `INSTRUMENTAL_MODELS` = `model_bs_roformer_ep_317_sdr_12.9755.ckpt`, `COROS_MODELS` = `mel_band_roformer_karaoke_aufr33_viperx_sdr_10.1956.ckpt`, each with its YAML config plus the shared `download_checks.json`. |
| `openssh-server`, `ca-certificates` | Vast's SSH launch mode needs an sshd in the image. |
| `/content/colab_sep_work` | The generated script hardcodes `/content` for the uploaded input and for its work directory. |

The image does not need network access to separate: **verified with `--network none`** (see below).

## How the models resolve

The script generated by `src/infra/vocal/colab_remote_script.rs` calls the
`audio-separator` CLI with only `--model_filename`, so the model directory has
to resolve from the environment. Three things guarantee it:

1. `ENV AUDIO_SEPARATOR_MODEL_DIR=/opt/models` — `audio_separator` reads this
   variable and it wins over the `--model_file_dir` default.
2. `/etc/environment` carries the same value plus `/opt/venv/bin` on `PATH`.
   Vast's SSH launch mode replaces the image entrypoint and does not guarantee
   that image `ENV` reaches an SSH session; `/etc/environment` does, because PAM
   reads it for login shells. This is also what Vast's own docs tell custom
   images to do.
3. `/tmp/audio-separator-models` is a symlink to `/opt/models`. That is
   `audio-separator`'s own default for `--model_file_dir`, so the script works
   even in a session with no environment at all.

## Why the probe failed (`pip install audio-separator[cpu]`)

Reproduced locally on `pytorch/pytorch:2.5.1-cuda12.4-cudnn9-runtime`
(python 3.11, no `-q`):

```
Building wheels for collected packages: diffq
  × Building wheel for diffq (pyproject.toml) did not run successfully.
  ╰─> building 'diffq.bitpack' extension
      gcc -pthread ... -c bitpack.c -o build/temp.linux-x86_64-cpython-311/bitpack.o
      error: [Errno 2] No such file or directory: 'gcc'
ERROR: Failed building wheel for diffq
```

`audio-separator` declares `diffq` unconditionally (it is not behind an extra,
so `[cpu]`, `[gpu]` and a bare install all pull it), and there is no linux wheel
for it. The `*-runtime` PyTorch images ship no C toolchain, so the build dies
immediately. It is not a network, quota or mirror problem: on the same image
with network and DNS working, the failure is the missing `gcc`, and in the probe
itself the `-q` plus suppressed stderr hid exactly this message.

This image compiles `diffq` in a builder stage that has `build-essential`; the
runtime stage keeps only the finished `/opt/venv`, so the compiler is not
shipped.

## Size

**13.5 GB** on disk (`docker image inspect` → `13_516_915_871` bytes), ~4.86 GB
compressed in the registry, for `linux/amd64`. The largest layers:

| Layer | Size |
| :--- | :--- |
| `COPY /opt/venv /opt/venv` (torch cu124 + audio-separator + onnxruntime-gpu) | 6.47 GB |
| `COPY /opt/models /opt/models` (two checkpoints + their YAML) | 1.55 GB |
| `apt-get install ffmpeg libsndfile1 libsamplerate0 openssh-server ca-certificates` | 475 MB |

The two models alone are 639 MB + 913 MB, so two thirds of "half the image
without models" is the CUDA-enabled PyTorch build. The equivalent `nvidia/cuda`
base image is ~9.6 GiB before ffmpeg or the models, which is why this image is
built from `python:3.10-slim-bookworm` plus the cu124 wheels instead.

## Pinning

`torch` is pinned twice on purpose. `audio-separator` only declares
`torch>=2.3,<3`, so a plain `pip install audio-separator` 
replaces the cu124 build with whatever the default index prefers — during this
work it silently produced `2.14.1+cu130`, a build that needs a newer driver than
the CUDA 12.4 hosts this image targets. A constraint file pins `torch` for the
rest of the build, and a build-time assertion fails the image if
`torch.__version__` or `torch.version.cuda` ever drift from `2.5.1` / `12.4`.

## How the adapter drives the image (T2)

`src/infra/vocal/vast_vocal_separator.rs` rents an instance through the Vast
REST API, generates an ed25519 key under `<data>/vast/ssh` (mode `600`), registers
the public key with `POST /ssh/`, and then uses plain `ssh`/`scp`:

1. `scp` the audio to `/content/input_audio`.
2. `ssh ... "bash -lc 'cd /content && python -'"` with the **unchanged**
   `generate_remote_script` on stdin. The login shell is deliberate: it is what
   loads `/etc/profile.d/venv.sh` in this image (see L11 of the task log).
3. `scp` `/content/colab_sep_work/output.mp3` back and verify SHA-256 and
   ffprobe duration exactly as the Colab adapter does.

Every HTTP and SSH call has its own timeout. The instance is labelled
`shirley-show`, kept warm for ten minutes after the last separation (including
a failed attempt while the machine proves healthy), and destroyed at once when
a health probe proves it dead. On application boot, `reap_orphans_on_boot()`
deletes every instance with that label so a hard restart cannot leave an orphan
billing; a periodic safety reaper does the same every five minutes for
instances that are not the current warm lease. The rent/pipeline work runs in
a detached task, so dropping the request future (agent deadline or client
disconnect) cannot skip the destroy or the retention timer; a rental that lands
after cancellation or its deadline is destroyed immediately. No key, token or
API credential is ever written to a log line.

The live Vast response shape is authoritative: `PUT /asks/{id}/` returns the
new instance id in `new_contract`; `GET /instances/{id}/` wraps the instance in
`{"instances": {...}}`, reports `actual_status` (`loading`, `running`,
`exited`, ...) and exposes direct SSH as trimmed `public_ipaddr` plus the string
`ports["22/tcp"][0].HostPort`. The adapter also accepts unwrapped responses,
legacy `status`, and proxy `ssh_host`/`ssh_port` when the direct port is absent.

### Control-plane API versions and filters

- `POST /api/v0/bundles/` validates **every filter as an operator object**:
  `{"eq": true}`, `{"gte": 0.99}`, `{"in": [...]}`, `{"lte": <max_dph>}`.
  Scalars produce HTTP 400 `bad_request` with
  `"<field>: Input should be a valid dictionary"`. The GPU whitelist is sent
  as `gpu_name.in` (including `RTX 4080S`); `limit` is 100 so a page of cheap
  CN offers cannot hide non-CN offers. CN/HK stays a client-side check on
  `geolocation`, never an API filter.
- Real bundles rows carry `verified` as null/absent (the server already
  filtered on it) and report `gpu_ram`/`disk_space` as fractional numbers, so
  the client-side check only rejects an explicit `verified: false` and parses
  those fields as floats.
- `PUT /api/v0/asks/{id}/` must send `client_id: "me"` and
  `runtype: "ssh_direc ssh_proxy"` (not `"ssh"`), plus image, disk and label.
- Listing moved: `GET /api/v0/instances/` returns HTTP 410
  `deprecated_endpoint`. Both the boot orphan sweep and the five-minute safety
  reaper use `GET /api/v1/instances/`, with
  `select_filters={"label":{"eq":"shirley-show"}}` and `next_token`
  pagination. The label is still checked client-side and the parser accepts a
  wrapped `instances` array, an object map, a bare array/object or a `data`
  wrapper. Single-instance `GET`/`DELETE` and `ssh/` stay on v0.

Observability follows the repository convention (`eprintln!`, no new crate):
`[vast] INFO` / `[vast] WARN` lines cover offers found and chosen GPU, dph and
geolocation, rent result, state transitions, ssh readiness, upload/script/
download timings, verification, retention/destroy and reaper actions. HTTP
errors include the endpoint path, status and a response body truncated to 300
characters with the API key scrubbed. The key and the `Authorization` header
are never printed.

## How it is built

Locally, without pushing:

```sh
docker build --network host -t shirley-vast-worker:local docker/vast-worker/
```

`--network host` is only needed on a machine whose Docker bridge has no working
DNS resolver; it is not a property of the image.

In CI, `.github/workflows/vast-worker-image.yml` builds on every change under
`docker/vast-worker/**`, on `main` (and on PRs, without pushing), and on
`workflow_dispatch`. It pushes `ghcr.io/loonbac/shirley-vast-worker:<git-sha>`
and `:latest` using `GITHUB_TOKEN` with `permissions: packages: write`. Before
pushing it smokes the image with `--network none`: `audio-separator --help`, both
model files present under `AUDIO_SEPARATOR_MODEL_DIR`, and `/content` existing.
Only the workflow pushes; local builds stay local.

## Using it on Vast.ai (owner step)

1. **Make the GHCR package public.** GitHub creates it private on first push.
   Go to `https://github.com/users/loonbac/packages/container/shirley-vast-worker/settings`,
   "Danger Zone" → "Change visibility" → "Public". Without this a Vast host
   cannot pull the image anonymously. (The alternative is adding a registry
   credential to the Vast instance, which would put a token on a rented machine
   — not recommended.)
2. **Create a template** in the Vast console pointing at
   `ghcr.io/loonbac/shirley-vast-worker:<sha>` (pin the SHA in production, not
   `latest`, so a rebuild cannot change behaviour silently).
3. **Launch mode**: `SSH` (or `Jupyter + SSH`). Vast then replaces the image
   entrypoint with its own setup script and starts sshd on internal port 22;
   the image's `CMD ["sleep", "infinity"]` is not used. Any environment variable
   the adapter relies on must be exported into `/etc/environment` from the
   template's on-start script, because Vast does not pass template env vars into
   SSH sessions:
   ```sh
   env >> /etc/environment
   ```
   `AUDIO_SEPARATOR_MODEL_DIR` and `PATH` are already in `/etc/environment` in
   this image, so nothing is strictly required for separation.

   Vast's own note: in `entrypoint` launch mode nothing is injected and no SSH
   is provided, so `SSH` is the mode the adapter must use.
4. **GPU choice**: a 24 GB card separates these models fine. Measured Vast
   prices: RTX 3090 ~$0.17-0.26/h, A5000 ~$0.21/h, 4090 ~$0.38-0.46/h. Prefer
   those over a Blackwell-class card (the user's instruction: "mejor busca una
   grafica economica en ves de una blackwell").

## Verifying the image

A full separation on CPU, with no network, against a 20s synthetic input (the
acceptance check for this image):

```sh
docker run --rm --network none -v /tmp/smoke:/work shirley-vast-worker:local \
  bash -lc 'cp /work/input_audio /content/input_audio && python /work/chorus_script.py'
```

It must print a single JSON line (`url`, `sha256`, `duration`, `size`) and leave
`/content/colab_sep_work/output.mp3`. Observed result is recorded in
`odd/tasks/vast-gpu-fallback.md` (L10).

Quick non-separating check of the contents:

```sh
docker run --rm --network none --entrypoint bash shirley-vast-worker:local -lc \
  'python -c "import torch, audio_separator; print(torch.__version__, torch.version.cuda)"; \
   ls -1 /opt/models; readlink -f /tmp/audio-separator-models'
```

## Known limits

- **amd64 only.** No arm64 build; Vast's arm hosts (GB200) are out of scope.
- **CUDA >= 12.4 driver required.** The cu124 wheels run on a newer driver; an
  older host driver cannot.
- The image does not start sshd itself (Vast's launch mode does) and does not
  listen on any port.
